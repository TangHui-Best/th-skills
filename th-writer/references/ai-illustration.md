# AI 原创配图建议

适用于需要提出或制作 AI 原创插图建议的任何文章模式。它只处理生成图的理解目标、内容边界与 prompt 委派；热点科普中的原始视频、截图、原帖、嵌入与授权问题，仍由 `hot-tech-explainer.md` 处理。

AI 原创图的任务是把已经由正文说明的局部关系、对象、动作或结果变得可感知，而不是替代证据、媒体来源或正文论证。技术文章中的 Mermaid、表格和代码块用于传达**精确关系与可核验事实**；AI 图解插画用于帮助读者建立直觉。不要用生成图替代状态图、时序图、参数关系或源码证据；但也不要把 AI 图退化成与论点无关的科技氛围图。

以下方法可跨文章模式使用，不将技术解析的证据骨架套用于其他模式。作者负责说明读者的理解需求与内容边界，作图 AI 负责视觉方案；出图后，再根据真实阅读问题修订。目标不是模仿特定作者的笔触，也不是让每张图都成为同一种技术图解。

## 先判断这张图属于哪一种

| 类型 | 可以承担什么 | 不可以承担什么 |
|---|---|---|
| 封面或章节氛围图 | 建立主题情绪、给长文留出呼吸 | 机制解释；不能算作文章的关键图解 |
| 机制图解插画 | 用视觉叙事或可理解的隐喻解释一个局部问题，例如「大结果为何外置」「Compact 后如何重建工作视图」 | 概括整篇文章全部概念；不能让读者靠猜测补出关键关系 |
| 精确技术图 | 状态、时序、阈值、字段、互斥条件 | 不应交给生图模型猜测；优先 Mermaid、表格或人工绘制 SVG |

用户说「想插入 AI 生图」而又希望图片帮助理解时，先判断关系是否需要精确表达：技术文章中，若当前关系必须精确到字段、比例、时间或源码分支，应明确建议改用 Mermaid 或可编辑图表；不要为了保留生图而降低正确性。若需要建立局部机制直觉，默认选择「机制图解插画」，不是封面图。

## 先找读者理解缺口，再决定是否配图

提出正文插图前，先说明：读者从相邻文字已经知道什么，仍难以直观理解什么，图片能增加什么。优先选择已由正文讲清事实、但读者仍对局部关系缺少直觉的位置。若一段例子已经足够清楚，图片只能把结论做成口号，或重复已有 Mermaid，就不必配图。

机制插图应围绕一个局部问题，使关键对象、变化及其后果可以辨认和复述。不要求每个概念对应一个物件，也不规定对象数量、单向阅读、左右对比或流程图。对机制的准确表达是约束，物件、布局和表现手法不是默认约束。

完整长文通常在正文之外给出少量可选配图建议，不为每个章节凑图。正文没有配图也必须可独立发布。除非用户明确要求生成图片，否则只给建议，不生成文件、不插入占位符。

## 生图 prompt 是独立的语义简报

中文文章的提示词默认用中文。假定作图 AI 没有读过文章，也不知道前文术语：将 prompt 单独复制后，它仍应能理解任务。自包含靠补足必要背景与关系，不靠作者预先完成视觉设计，也不靠粘贴整段文章。

按实际需要覆盖以下信息，不强制固定标题、段数或顺序：

- **用途与理解目标**：用于正文、封面还是其他位置；希望图片帮读者理解哪个问题，而非只给出主题名或一句结论。
- **必要背景**：用日常语言解释相关机制；陌生术语当场说明，只保留影响本图理解的内容。
- **具体例子与关系**：必要时给出输入、发生的变化和后果。示意案例应标明为示意，不能伪装成用户经历或产品实测；强调不能画错的因果、条件、范围或系统分工，而非指定如何画。
- **内容边界**：说明是通用原则、某版本实现还是作者建议；不把概念示意画成真实产品界面或无来源的能力证明。哪些差异需要可辨认可以说明，但不强制用分区、边框或角标实现。
- **视觉委派与交付要求**：把视觉叙事、构图、隐喻、物件与艺术风格交给作图 AI。尺寸、参考风格、品牌元素等仅按用户要求或实际发布需要选择，不把横版 16:9 或本次案例变成通用规格。

正文插图应有视觉吸引力并减轻理解负担，不能只将已有结论排成口号海报。文字仅作必要辅助；中文应清晰，不规定标签数量，也不默认无字。若模型文字渲染不可靠，可留待后期补字，但不能让关键语义因此丢失。

不要附一份跨文章的装饰禁令，也不要默认限定扁平矢量、三维、写实或某套配色。判断依据是视觉元素是否帮助表达、是否误导或抢走注意力，而非它属于哪一类。用户已明确指定的风格或构图应尊重；作者提出的视觉灵感若确有价值，注明可选，并允许作图 AI 换成更合适的方案。

## 分开作者审阅信息与可复制 prompt

每条建议先简要交代插入位置、读者理解缺口、图片增量、图像类型、内容边界与建议图注，再提供可完整复制的中文生图 prompt。与表达无关的字段可以省略，不再要求一份独立的构图说明或标签清单。

作者审阅信息用于判断是否值得配图；prompt 用于委派设计。必要背景与内容边界应在 prompt 内完整表达，不能依赖外面的字段、章节名称或「如上所述」。

## 语义简报示例

以下是《Agent 记忆系统设计综述》配图迭代中的示例，展示沟通方式，不是所有文章必须照搬的题材、尺寸、段落或禁令：

```text
请为一篇关于 AI Agent 记忆系统设计的中文技术博客创作一张正文插图，横版 16:9。

这张图需要帮助读者理解一个机制：信息被保存下来，不代表它的原意也被完整保留。Agent 将对话整理成记忆、再用于未来任务时，可能丢掉原话的适用条件，把局部要求变成全局规则。

背景示例：用户说：“这次给董事会的报告写详细一点，日常汇报仍然保持简洁。”

如果整理后的记忆只剩下“用户喜欢详细报告”，就丢失了“本次、董事会报告”这些条件。未来处理日常汇报时，Agent 可能因此采用错误的默认方式。

合理的处理应保留原话的依据和适用范围：这是一项针对本次董事会报告的要求，不足以修改用户对日常汇报的偏好。信息仍然值得保存，但后续使用不能超出它的条件。

希望图片让读者直观看到：同一条信息经过整理后，可能变得更短，却也可能改变意思；保留来源和条件，才能帮助未来的 Agent 判断何时可以复用它。

请自主决定最合适的视觉叙事、构图、隐喻和艺术风格。不要只把结论排成一张对错海报，也不必采用流程图。重点是让“信息如何发生变化，以及这种变化为什么影响未来使用”变得可感知。

这张图会插在技术文章的正文中。希望它有视觉吸引力，同时能减轻理解负担；文字仅作必要辅助，不需要重复整段解释或放置巨大的口号标题。如使用文字，请使用清晰的中文。

这是通用设计原则的示意，不是某个产品的真实界面。除上述语义与用途要求外，视觉表达交给你设计。请直接生成图片。
```

示例末句是复制给作图 AI 的任务，不代表写作 Agent 获得了生成图片的授权。这组实践支持改进委派方式，不证明「约束越少，图片一定越好」。

## 出图后从读者视角审视与修复

审阅时以图片是否适合正文为标准，不以「比上一版好」代替验收：

- 图片是否使难以理解的关系变得可感知，而非只将文字放在漂亮物件上？读者能否看出发生了什么，以及为什么影响结果？
- 隐喻是否容易解码？不同路径、条件与后果是否混淆？有没有暗示正文未支持的事实？
- 装饰是否服务内容，还是与主要信息争夺注意力？图片是否打断文章阅读，变成另一张封面或宣传海报？
- 放到预计正文宽度后，关键内容是否仍可读？涉及移动端验收，应查看实际缩放预览；没有查看时只能指出风险，不能声称已经验证。

已有有效视觉方案时，修复 prompt 应附上当前图片，说明值得保留的部分，以及具体的阅读障碍和希望改善的效果，让作图 AI 选择修复方法。不要因为局部问题重设整套风格，也不把修复这张图所需的物件、连线或布局推广为未来所有 prompt 的规则。若核心隐喻本身无法解释机制，再重新设计。
