# 热点技术科普模板

适用于「某项技术突然很火，但大多数读者尚不知道它是什么、能做什么、和已有技术有什么不同」的中文博客。目标是先建立准确直觉，再解释机制；不是把发布公告改写成软文，也不是把一份技术文档压缩成术语清单。

## 写前素材卡

先填这张卡。缺少第一项时，不要直接起草首屏；先找真实 demo，或把开头收缩为一个可验证的原帖/界面事实。

```text
研究对象：产品/模型名称、版本或发布快照、访问日期
目标读者：已经听说它很火，但尚未形成基本概念的人
读者最可能的误解：例如「它会直接控制电脑」或「它就是一个更快的大模型」

直觉证据：一个可看见的真实动作；视频/动图/界面/原帖的链接与来源
系统拆解：调用方给什么输入、模型输出什么、代码/人/规则分别执行什么
最小定义：一句不依赖专有名词的日常语言
关键差异：和读者熟悉的旧方案相比，哪一项输入、输出或责任边界改变了
可迁移场景：两个或三个，必须标注「已展示」或「作者推断」
性能与成本：原始来源、比较对象、条件、厂商主张或独立验证的状态
不可推出的结论：不保证什么；风险/授权/可靠性仍由谁承担
```

## 首屏模板

首屏不追求把所有信息讲完，只完成一个闭环：**看见动作，辨认分工，获得定义。**

```markdown
<标题：以读者的困惑或对象的最小定义为中心，不用空泛性能口号>

<一张原始截图或一句来源事实，可选；只说明为什么此事值得看>

<可直接播放的真实 demo；不可嵌入时放关键帧与来源链接>

*图注：画面中发生了什么；模型只负责哪一步；哪一部分仍由普通软件负责。*

<用两到四句把画面拆开：输入/候选项/输出/执行者。>

> <对象> 本质上是……

<用一个读者熟悉的第二场景，将该定义迁移一次。>
```

### 首屏反例

以下内容通常不应作为第一个案例：

- 只有“未来可能改变某行业”的商业设想；
- 需要先理解投放、增长、金融、代码架构等背景才能看懂的例子；
- 展示最终效果，却看不见模型在系统中承担何种动作的案例；
- 只展示创始人履历、浏览量、融资金额或“快 N 倍”的宣传图。

这些可以留在第二屏以后：前者用于讨论应用价值，后者用于说明事件与来源。

## 正文模板

### 1. 它在 demo 中究竟做了什么

沿用首屏案例，用一个短流程回答：

```text
当前状态/上下文
        ↓
调用方提供的合法候选项或任务约束
        ↓
模型输出选择、分数、结构化结果或建议
        ↓
代码、业务规则或人执行并承担后果
```

图后明确说明：这幅图中哪些是原始材料的事实，哪些是为便于理解做的抽象。

### 2. 用最少术语解释它是什么

先给日常定义，再引入产品术语、接口名或训练方法。首次出现的术语至少回答：谁在何时输入什么，它输出什么，这个输出改变了谁的下一步。

### 3. 它和读者熟悉的东西哪里不同

只比较真正会影响使用判断的维度，不罗列品牌或跑分。适合用表格：

| 对比对象 | 输入与输出 | 谁定义边界 | 适合什么 | 仍不解决什么 |
|---|---|---|---|---|
| 旧方案 |  |  |  |  |
| 本文对象 |  |  |  |  |

先公平说明旧方案何时足够好，再解释新方案改变的约束。不要把“更强”当作差异本身。

### 4. 它能迁移到哪里

每个场景都按同样句式写，避免把想象写成产品清单：

```text
场景：……
已知输入与候选项：……
它可能承担的判断：……
真正执行者与安全边界：……
证据状态：官方演示 / 社区 demo / 作者推断。
```

### 5. 热度之外，哪些结论还不能下

至少保留一组具体限制：数据来源、候选项质量、延迟、成本、置信度校准、权限控制、业务后果或评测范围。不要用泛泛的“仍待时间检验”代替实际边界。

### 6. 结尾：回到最初画面

用首屏 demo 中的分工回扣核心判断。结论应回答“为什么值得关注”和“为何不该神化”，而不是重复标题或预言整个行业。

## 热点科普的排版与节奏

热点技术文章常同时有 demo、定义、流程、性能数字和资料来源。它们不能全写成短段落或深色代码块；Markdown 的任务是让读者在扫读时就能识别信息性质，而不是给每句话增加装饰。

### 先决定一段信息应该长什么样

| 信息类型 | 优先形态 | 不宜使用的形态 |
| --- | --- | --- |
| 对案例、机制或差异的连续解释 | 2 至 4 句的完整段落 | 连续的一两句独立段落 |
| 一句话最小定义、厂商主张、风险提醒 | 引用块；必要时加简短标签 | 普通段落里淹没，或将整章都写成引语 |
| 状态、候选项、输出者、执行者之间的稳定映射 | 两到四列的短表格 | 多段重复解释，或伪装成代码 |
| 有先后关系的工作流 | 编号步骤；仅在关系本身是核心论点时使用简短流程图 | 为了画箭头而堆叠多行代码块 |
| 原始页面元素、API 输入输出、命令或可复制模板 | 代码块 | 仅仅想突出一句自然语言时 |
| 来源、许可、研究范围 | 收束的列表；长文可使用平台确认支持的折叠区 | 结尾一整堵免责声明式文字 |

表格必须压缩真实的比较或映射，不能只是把一段话拆成格子。移动端优先两到三列；若字段更多，拆成两张表或改为列表。

### 段落与标题的层次

- 一般解释先写成完整段落，再决定哪些句子需要独立出来。连续出现三段以上的一句段落时，检查是否只是把正常推理切成了逐行讲稿。
- `##` 只承载文章的主问题或主转折；`###` 承载同一主问题下的案例、机制或边界。不要把每个论点都升格为同级标题，也不要让同一篇长文只剩一串没有从属关系的 `##`。
- 标题应帮助跳读，不能只是把紧邻段落改写一遍。若删掉标题不影响读者定位该段职责，优先不用标题。
- 让每一种媒体只承担一个主要任务：首个真实 demo 说明“发生了什么”，截图说明“为什么被讨论”，表格或流程补上“谁负责什么”。不要让图、视频和正文三次复述同一信息。

### 最后一遍版式复核

在事实检查之后，按以下顺序浏览成稿：

1. 只看首屏：是否先看到真实行为，再看到分工和最小定义，而不是先被热度截图、履历或性能口号占满？
2. 只看段落首句：连续阅读时是否存在无新增信息的短句重复、反复否定同一误解或同义转场？
3. 只看非正文元素：表格、引用块、代码块和媒体是否各有唯一职责，代码块是否只保留原始结构或可复制内容？
4. 只看标题与末尾：标题是否呈现主次关系；资料与边界是否方便回查，却没有盖过结论？

若任一检查失败，先合并段落、删去重复的边界解释、替换错误的 Markdown 组件，再考虑增写内容。

## 媒介使用检查

### 视频与动图

- 是否可在目标发布平台直接观看？若不行，是否有关键帧、图注和原始跳转链接？
- 画面是否让非专业读者也能看出一个动作或状态变化？
- 视频旁是否写清模型的输入、输出和非职责，防止读者把运行画面误读为端到端能力？
- 是否获得了适合嵌入/转载的授权，或只使用源平台的官方播放器？

### 截图与图片

- 图片是在证明产品存在、呈现真实行为，还是解释机制？每张图只能承担一个主要职责。
- 图片是否标注原始链接、作者或机构？
- 浏览量、转发量与名人背书是否只作为事件背景，没有被写成效果证据？
- 是否删掉会分散主线、泄露个人信息或误导时间线的界面元素？若截图本身就是热度证据，可保留，但应在图注说明。

### 文字

- 视频加载失败时，读者能否仅通过图注和文字理解案例？
- 文字是否避免复读画面，而是补上画面看不见的状态、候选项、权限与边界？
- 每一个性能数字、产品结论或未来场景，是否能追溯到明确来源或清晰标注为作者判断？

## 发布前的 30 秒复述测试

把首屏交给不了解对象的人，或假设一位不了解对象的读者只看首屏。检查其能否回答：

1. 画面中模型具体做了什么？
2. 画面中仍由软件或人负责什么？
3. 因而这个技术最简单的定义是什么？

若任一题只能得到“它很聪明”“它能自动化”“它很快”这样的答案，说明首屏还没有建立正确心智，应先重选案例或重写图注，而不是追加更多术语。
