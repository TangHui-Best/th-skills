# 技术解析文章规范

适用于源码解读、系统架构、实现机制、协议、论文和工程设计文章。目标是让读者既能顺着文章理解，又能分辨哪些结论来自证据、哪些来自作者的工程判断。

## 本文件怎么用（阅读地图）

本文件按技术解析的三个写作阶段组织：同一阶段的章节回答同一类问题，跨阶段有明确依赖。每个 `##` 标题后标注了它服务的阶段，跳读时以本表为准。

| 阶段 | 何时读 | 对应章节 | 本阶段产出 |
|---|---|---|---|
| 动笔前 | 确定选题、核对材料时 | 写前证据骨架、证据与措辞（含选题张力与读者入口） | 一个具体研究问题、一个中心判断、一份证据清单 |
| 起草中 | 组织正文、写机制与图表时 | 写作结构、Markdown 视觉层次、推荐收束 | 可发布的初稿正文 |
| 起草后 | 自检、处理外部反馈时 | 理解检查、审阅反馈的取舍、发布前核验 | 通过复核的终稿 |

阶段之间的依赖：

- **动笔前 → 起草中**：动笔前确定的「中心判断」决定起草时保留哪些章节、砍掉哪些材料；证据骨架里的缺项应在起草前处理，不带进正文用流畅叙述掩盖。
- **起草中 → 起草后**：起草后各节只以**实际正文**为依据，不用写作计划、作者意图或此前讨论补足稿件。
- 需要提出或制作 AI 原创配图建议时，读取跨模式的 [AI 原创配图建议](ai-illustration.md)；其他模式引用它时，不因此套用本文件技术解析的证据骨架。

## 写前证据骨架 · 动笔前

在写作前从材料中整理下列信息。缺项时不要用流畅叙述掩盖它；根据影响程度向用户询问、限定论断，或明确标记为待确认。

| 项目 | 要回答的问题 |
|---|---|
| 研究对象 | 什么项目、版本或快照、访问日期、适用范围是什么 |
| 核心问题 | 本文希望回答的一个具体问题是什么 |
| 中心判断 | 作者对设计的总体解释或反直觉发现是什么 |
| 作者角度 | 作者最初的困惑、被哪项证据修正的旧理解，或最想留下的工程判断是什么；仅使用用户提供的真实材料 |
| 机制证据 | 哪些文件、函数、数据结构、配置、日志或实验直接支持主张 |
| 运行链路 | 事件按什么顺序发生，状态在哪里创建、消费、失效和恢复 |
| 边界 | 哪些机制是实验性、默认关闭、版本特定，或没有完整实现 |
| 代价 | 设计获得了什么，又牺牲了成本、精确性、时延或复杂性中的什么 |

不要把「代码里出现一个名字」写成「产品稳定具备某能力」。不要把注释中的意图写成已经被运行时行为验证的事实。

作者角度不是每篇技术文章都必须写成第一人称故事。它的作用是让文章有一个不能被任意替换的研究问题或判断。若用户没有提供真实的困惑、发现或经历，不要编造“我看到这里愣住了”之类的反应；可以保持中性说明体。

### 选题张力与读者入口

完整技术博客在动笔前，除核对证据，还应检查三个入口是否成立：

- **问题张力**：是否存在一个具体矛盾、反直觉现象或真实决策，使读者愿意追问下去。
- **知识增量**：文章是否能提供源码证据、机制解释或取舍判断，而非复述常识。
- **工程共鸣**：问题是否对应目标读者实际会遇到的成本、失败模式或决策压力。

这不是要求每篇文章煽情或追逐热点。若其中一项不足，优先用可核验的运行片段、代码路径或更准确的标题澄清问题；不要用虚构场景、情绪或夸张承诺填补张力。

## 证据与措辞 · 动笔前

使用能表达确定性的措辞。

| 证据强度 | 推荐写法 |
|---|---|
| 直接由代码路径、测试或运行结果确认 | 「当前研究样本中，X 会在 Y 后执行」 |
| 注释、命名或局部代码支持，但缺完整调用侧 | 「代码显示其设计意图是…，完整行为仍需调用侧确认」 |
| 作者归纳 | 「我认为这套设计的取舍是…」 |
| 假设或版本敏感内容 | 「若后续版本未改变该边界，则…」 |

避免「永远」「全部」「必然」「完全保证」等绝对表述，除非源码确实在所有相关分支上提供了这种保证。

## 写作结构 · 起草中

开头可以从使用中的困惑或源码研究的发现进入，尽早明确本文研究什么、中心判断是什么。一般研究范围与方法说明可后置，不为完整性在前言堆叠声明；决定某项主张能否成立的版本、样本或证据限制，应随该主张就地说明，不能只藏在文末。

当文章涉及多个机制、术语或实现层次时，开头还应给读者一份最小阅读地图。它不是目录复读，而应先说明：本文将按什么问题顺序推进；每一类信息或机制分别解决什么；读者先记住哪个总框架，再进入具体实现。没有这个总框架的机制拆解，容易退化成只适合作者本人回看的研究笔记。

对于多机制的技术长文，阅读地图通常需要两块互补信息，不能互相替代：

- **阅读路线**：文章将按什么问题、事件或压力升级顺序推进，帮助读者预判章节之间的因果关系。
- **读后收获**：本文希望回答哪些具体问题，帮助读者判断这篇文章是否覆盖自己的困惑。

阅读路线回答「这篇文章怎么读」，读后收获回答「本文希望解决什么问题」。两者可以各用一小段或一组列表呈现，但不要把其中一个删掉后让另一个兼任。面向读者的正文避免使用「读完后你应该能……」这类考核式措辞；由文章说明自身希望回答什么。

分类框架首次出现时，先说明分类对象和维度，并让读者当场知道各维度在讨论什么，不只列名称、等待后文解码。需要时将名称展开成实际问题或代表选项，例如「检索主权」可解释为「由 Agent 决定何时读取，还是系统检索后注入」。具体选项应属于同一比较层次；段落、列表或表格按理解需要选择，不必在前言提前展开全部实现。例如「信息生命周期」应说明它分类的是 Claude Code 如何让信息跨轮进入、移出和恢复模型工作视图，而不是信息在业务上的自然生命周期。若一个机制横跨多行分类，明确写出它跨越哪些类别；不要用「A 只是表中某一行的实现」这类会把多阶段机制错误缩减为单一职责的表述。

首次出现的专有术语必须先给出最小可用定义，再讨论它不是什么、与什么不同或为何横跨多个类别。最小定义至少回答「谁在何时做什么，结果改变了什么」。不要假设标题、目录或后文会替读者完成术语补全。

概念说明还应让读者知道为何需要它。区分「是什么」「解决什么问题或带来什么用户价值」「如何实现」，不能用机制职责替代目的，也不能只写目的而省略定义。用户价值无需由一种技术独占：例如「让 Agent 在持续使用中表现得更智能」可以是记忆系统的目标，「保存、维护和召回过去的信息」则说明实现路径。目标陈述不等于已经验证的效果保证；必要的条件与边界在展开中交代，不因追求严谨而将用户价值改写成另一套工程指标。

这些内容不必挤进一个长句，也不强制每章按同一模板展开。定义已被认可且准确时，可以只补一句目的；当段落已经解释充分时，优先提炼或前移观点，而不是再写一遍。概念章节应让读者辨认定义与关系，方案章节应留下取舍判断，不能只把材料按顺序罗列。

### 多维设计说明：把分类变成判断路线

当章节要帮助读者设计系统，而非仅介绍已有实现时，从读者需要作出的选择组织内容。例如，「认识几种召回方案」只是范围；「区分未发起查询与查询未命中，再选择补决策机制还是改检索算法」才是具体判断。以下方法用于形成与检查正文，不要求交付额外计划或为每节填同一模板。

#### 先建立系统关系，再安排阅读路线

- **知识分类用于覆盖问题**：维度清单是研究与查漏工具，不自动成为阅读路线。同层标题回答同层问题，纠误与局部难点归入对应问题；不强制标题都用问句或固定维度数量。
- **系统关系解释相互约束**：梳理关键对象、状态、处理责任与使用位置，明确一个选择怎样影响其他环节。例如，记录是否保留来源与作用域，会影响维护时能否纠正、召回时能否判断适用性。不要只说「这些维度相互关联」，而不指出传递的是哪个条件。
- **阅读路线服务理解依赖**：在关系明确后，决定读者先理解什么、后理解什么。运行链路、设计决策顺序与阅读顺序不必相同；反馈、并行或相互约束不能硬写成单向流水线。并列维度可以独立展开，但需交代共同目标与比较层次；治理、权限、评估等贯穿要求要落到受影响的选择中。

关系梳理可以是一段话或一张小图，复杂时再使用表格。它应帮助安排正文，而不是制造另一套需要读者记忆的分类。跨节承接应解释实际依赖或未解决的问题，不能用「接下来讨论」代替关系。

#### 先写清核心解释，再按理解缺口展开

先形成能独立回答本节问题的核心解释：有哪些值得比较的方案，按什么条件比较，为什么这些条件会影响选择。它可以是段落、列表或表格，不要求正文全部总结化。

新增细节应提供机制解释、条件差异、失败后果、证据或取舍依据。案例更多、术语更多、篇幅更长不等于更深；如果只是重复核心结论或增加产品名，应删去、归入资料区，或留到产品案例章节。

例如，「即时写入与后台提取可以结合」还不足以指导设计。展开需要解释：明确纠正若要求下一次任务生效，就不能只等周期整理；探索经验若依赖最终结果，结束后提取更容易获得完整依据。两种需求同时存在，才有理由承担双通道的协调成本。这是设计示意，不是某产品的实测结论，也不是每节必须照搬的句式。

正文与附录可以分工：正文解释条件、机制与选择理由，附录汇总方案便于查阅。但关键关系不能只放在附录，正文也不能只是把速查条目拉长；不强制每篇文章都设附录。

#### 案例取舍、展开深度与横向比较

引入案例前，确定它在回答哪个正在讨论的问题；正文提供理解所需的最小背景，并明确它展示的差异怎样支持本节判断。筛选时问：去掉这个案例，读者会失去哪条解释或依据？如果只少认识一个项目，不宜占据主线。

多案例文章按解释价值与证据深度决定篇幅：能解释一组关键选择且材料充分的案例可以完整展开；只补足一项区别的案例可以局部对照或简短补充；不能推进理解的案例可以不纳入。知名度和产品数量不决定篇幅，也不要求各案例填写同样数量的维度、拥有同等粒度的机制图。相似方案若面对不同约束，仍可能值得展开；公开资料不足则限定解释范围，不能把未公开机制写成不存在或能力较弱。

横向比较围绕同一个设计问题，区分机制职责、适用条件与代价，不仅罗列组件或功能。组件同名不保证职责相同，接口相似不保证底层实现相同；不同场景、版本和材料范围也不能直接排成先进程度。案例间的承接应指出本次转向哪项约束，不暗示后一个产品必然解决了前一个产品没有的能力。框架用于覆盖问题，比较用于揭示会改变选择的差异，不必再按全部维度复述案例。

例如，介绍程序性记忆时，先解释「记录完成过什么」与「保留以后可以怎样完成」的差异，再介绍可执行技能库，读者才能知道案例为何出现。此处不必提前展开索引、检索和调用链；完整产品机制可以后置。示意不能伪装成用户实测，真实案例也不能据此推出未经验证的普遍收益。

需要解释跨环节影响时，可以沿用一个背景完整的例子，但不要求贯穿案例或每节都有案例；已经解释清楚的背景不反复重讲。

修改框架时，检查它是否仍覆盖原有关键问题，而非因标题变简单就丢失约束；同步导语、表格与后文对框架的引用。只调整受影响的内容，不把局部结构修订扩展成全篇重写。

#### 从原则到设计推演与验证

当文章承诺帮助读者设计系统，而原则清单仍不足以支持选择时，用背景明确的设计推演展示目标怎样约束方案。已有案例若已承担这项职责，不必再造一个示例；没有实测材料时，可以明确标注假设场景，用于解释选择过程，不能作为效果证据。

推演应说明希望改变的行为、需避免的新增错误、作出选择所依据的条件，以及为何暂不采用其他机制。改变任务范围、信息规模、来源或风险等关键条件时，解释哪些选择需要调整。框架用来检查方案是否相互一致，不必重新展开为一套维度清单，也不强制固定步骤、贯穿故事或最小文件方案。

涉及“有效”“更可靠”等效果判断时，明确观察的是最终行为还是中间环节；提出验证方法时，交代比较对象、需要控制的条件、反例与额外代价。组件执行成功、命中数量增长或系统自报，不能单独证明最终任务改善。未实施的验证写成建议或待验证事项，不编造对照结果；不要求所有技术文章附完整评测。

提出改进建议前，沿实际链路区分可能的失败位置，说明用什么记录或现象辨别，再把修复对应到已定位的缺口。不要从同一个外部症状直接归因于某个组件或模型；也不要把“增加更强组件”作为统一解法。失败定位用于支持选择，不是另一套必须填满的分类表。

以下机制拆解规则用于有具体实现或运行链路的部分，不要求上述设计说明套入源码拆解模板。

### 机制拆解与运行链路

可采用的顺序是：领域压力或问题背景 → 常见方案及各自适用边界 → 作者的分类框架 → 个案源码拆解 → 全链路图 → 边界与工程判断。若实验能力会在文章中出现，先解释它们解决的通用问题，再引入名称和启用状态；不要在读者尚不知道术语含义时先要求其理解「主干与实验」的分界。

对于状态机、运行时、协议链路和多阶段工作流，先给出一张最小的端到端流程图，再拆解各节点。章节之间必须显式指出因果关系，例如「前一层只解决单条爆炸，仍未解决中小结果的长期累积，因此下一层需要 Compact」。不要仅依靠相邻标题暗示承接关系；读者应能解释上一节遗留了什么问题，下一节为何正好解决它。

关键机制可以形成一个小闭环：先给出可验证的具体矛盾或运行片段，再解释机制如何处理它，最后回扣该矛盾仍被保留的边界或代价。这里的“具体”优先来自日志、输入输出、代码路径或用户提供的真实研究过程，不得用假设性故事代替证据。

技术文章应把指代清晰度当作正确性的一部分。每个章节开头、每次从一个机制切换到另一个机制、以及跨句承接因果时，优先重申实体名称，例如「Claude Code 的 Auto-Compact」「大结果外置机制」「`readFileState`」，不要只写「它」「这一步」「这套机制」。代词仅在同一句或紧邻句中存在唯一明确先行词时使用。

个案机制拆解按读者的理解顺序组织，而不是代码目录顺序。局部小节聚焦一个机制单元，可以按以下顺序展开：

```text
机制的职责
→ 关键实现或数据流证据
→ 为什么需要它
→ 与相邻机制如何衔接
→ 它没有保证什么
```

当源码体现了有意义的方案选择，例如采用 A 而不是 B，不要止步于「A 的实现细节」。在不把作者推断伪装成源码事实的前提下，补上一段决策分析：当前代码确认选择了什么；可比较的替代方案有哪些；每种方案的收益、代价和适用场景；当前系统的约束为何更匹配 A。若源码没有直接说明选择动机，应明确写成「基于代码结构的工程推断」，而不是声称项目作者的真实意图。

比较替代方案时，先公平说明朴素方案为何被采用、它在什么条件下更合适，再解释当前系统的约束为何改变取舍。不要把对立方案写成明显错误的稻草人。

优先分析会改变系统边界的选择，例如触发策略、状态存储位置、缓存策略、同步或异步恢复、摘要或重读、局部清理或全量重建。不要为了凑体系化而给每个普通实现细节强行罗列方案。

如果多个机制共同完成一条链路，在需要整合关系的位置提供或回用全链路图。图展示对象与运行关系，正文解释选择理由与代价，横向表揭示差异；相互配合，不要求每种载体都重复完整解释。若前面的图已覆盖同一关系，后面可以回用，或只展示新增层次；仅换布局、风格或工具不构成保留重复图的理由。图、表、代码块只在能够减少读者认知负担或保留实体证据时使用，不限定每个案例的图表数量。

| 信息类型 | 更合适的表达 |
|---|---|
| 状态流转、异步关系 | Mermaid 流程图或时序图 |
| 参数、阈值、职责差异 | 对照表或计算式 |
| Prompt、协议、摘要、配置结构 | 经过脱敏和概括的模板骨架 |
| 单一关键结论 | 简短引用块或一段直接论证 |

不要逐字粘贴大段源码。应当保留会改变读者理解的结构、字段、阈值和控制分支，并标明它是「按源码整理的骨架」还是原文片段。

## Markdown 视觉层次 · 起草中

Markdown 不是排版装饰，而是帮助读者在长文中定位论点、证据与边界的第二条阅读路径。视觉锚点必须服务于论证，不能替代论证。

| 要突出什么 | 推荐格式 | 使用原则 |
|---|---|---|
| 核心定义、职责与目标、关系、依据性观点、设计判断或关键数字 | `**加粗**` | 强调可独立理解的关键语义单元；允许完整句或紧密关联的几句话，范围按理解需要而非句长决定 |
| 源码事实、工程推断、决策结论、能力边界、核心不变量 | `> **标签**：内容` 引用块 | 标签明确证据性质；「工程解读」不得伪装成「源码事实」 |
| 主线阶段切换 | `---` 分隔线 | 只用于认知框架进入机制拆解等大转场，不在每个小节之间滥用 |
| 并列且可独立成立的多个点，例如多个方案、失败模式、字段、检查项或枚举条件 | `-` 无序列表 | 各项顺序无关、增删不互相影响；有因果或依赖关系的推理链改用完整段落或编号步骤，不拆成一句一条的碎片 |
| 多方案、状态映射、参数对比 | 表格 | 列维度必须帮助做判断，例如优点、代价、适用场景 |
| 流程、时序、状态转移 | Mermaid 图 | 图应压缩关系；图后用一两句说明读者应该从图中看到什么 |
| 模板、计算式、协议骨架、工具输出 | 代码块 | 保留结构，删除与理解无关的原始细节 |

技术解析长文通常应在重要机制段落提供一个可扫描锚点，但不要求机械地每节都用同一种格式。锚点应承载真实的定义、关系或判断，而非仅标记「很重要」或列出概念名。顺读正文可以理解推理，扫读重点也应拿到主要认识；重点不必包含全部论证，却应保留避免误解所需的对象、条件与证据归属。正文不因增加重点阅读路径而改成摘要清单。

优先使用 CommonMark 和目标平台稳定支持的元素。不要假设颜色、HTML、折叠组件或平台私有的 admonition 样式一定可用；若用户未指定发布平台，使用标题、加粗、引用块、无序列表、表格、分隔线、代码块和 Mermaid 即可。

## 推荐收束 · 起草中

技术文章的结尾不必追求宏大升华。最好的收束通常回到开头问题，说明机制如何回答它，再留下一个仍未被设计硬保护的状态、一个成本，或一个值得继续验证的改进点。

若核心机制与某个更古老、更成熟的领域方案同构（操作系统、数据库、分布式系统等），可以做一次受控的参照物升维，两段式执行：机制首次讲透处用一两句埋入类比，建立直觉；结论处点破同构与关键差异；作者的工程建议若在参照物中有现成概念，用该概念为建议命名，例如「小型任务契约」对应操作系统的「钉住的页」。约束：全文最多一次，它是上限不是配额；类比只承担直觉建立与记忆锚点，不承担论证；差异必须显式写出；不引入未经核验的历史细节；不得把类比写成源码事实。

## 理解检查：检查正文实际提供了什么 · 起草后

扫读检查验证重点是否可定位且自身传达了主要认识，理解检查验证正文解释是否成立。起草或重写后，仅依据正文和已明确的目标读者背景检查，不用写作计划、作者意图或此前讨论补足稿件；不必向用户展示内部检查清单。

- **收获检查**：不照抄标题，用日常语言概括本节解释清楚的关系或选择依据，并指出正文中支撑它的解释或证据。若只能列出术语、产品名，或复述一句没有展开的结论，本节尚未建立具体收获。
- **全篇增量检查**：在前文已建立的理解之上，本章新增了什么解释、证据或判断？单章清楚不代表独立成章有价值；主要承担回顾或导航时，检查是否适合并入前章、结尾或附录。相同主题可以在定义、案例、比较和设计应用中再次出现，但须承担不同职责，不能只换措辞复述。按实际理解需要决定分工，不强制采用这组章节顺序。
- **关系检查**：说明相邻小节共享的对象或目标，以及前一选择如何约束后一选择。若声称按因果或依赖顺序展开，却可以任意交换而不影响解释，需检查是否只有过渡句，没有实际关系；真正并列的内容不强求先后依赖。
- **迁移检查**：对设计指南，选一个改变关键条件的新场景，判断正文是否提供了调整方案的依据。例如，单用户助手变成多用户办公助手，哪些原有选择因作用域、并发或审批需求而需要重新考虑？不要求替所有场景给出完整架构；若只能照抄某产品，需补足适用条件与推理。

发现缺口时，区分关系未建立、论证不足、背景缺失与呈现不清，再修改对应部分；不以增加加粗、篇幅或案例数量代替修复。内部检查通过只能说明已完成编辑复核，不等于真实读者验证；用户认可标题或框架，也不代表展开已验收。不要声称写作规则能保证阅读效果。

## 审阅反馈的取舍 · 起草后

“AI 味”检测器或外部审稿意见提供的是**编辑信号**，不是必须逐项执行的禁令。技术文章的修订优先级应是论证准确、证据边界和读者理解；不要为了降低某个形式频次而删掉真实的方案比较、状态区分或导航结构。

收到相关反馈时，先逐项判断：这段文字是否在澄清概念、比较真实方案、标注证据性质、建立章节承接，或说明能力边界？如果删改会损失这些功能，应保留其论证职责，只消除可替代的修辞外壳。

- **重要性标签**：避免用「文章最重要的判断」「先记住这个结论」「更重要的是」替读者宣布重要性。改用能说明对象或缺口的标题，例如「核心框架」「任务契约：仍未被硬保护的缺口」；结论是否重要应由位置、证据和展开本身建立。
- **对比句**：核心定义与判断优先正面陈述，不为表达本质而预设反驳对象。当对比纠正常见误解、比较真实备选方案或划定机制边界时保留，不按出现次数机械清除「不是 A，而是 B」。
- **Markdown 标签**：`源码事实`、`工程解读`、`决策结论`、`能力边界` 等标签属于证据分层，不等同于情绪性加粗或营销式强调。维持稳定的标签语义；需要收缩时，删除无信息的强调词、重复或不服务理解的强调，不因加粗包含完整句或多句而机械删除。
- **重复结构**：多阶段机制采用一致的「职责 → 证据 → 取舍/边界」骨架，能降低读者切换成本。只有当各节没有新增事实、推理或不同证据形态时，才打散或合并结构。
- **收束标题**：技术文章的最后一级标题应复述中心判断或回答开头问题，避免只写「结尾」「总结」等无信息标题。

## 发布前核验 · 起草后

- 版本、日期、仓库来源和研究范围可追溯。
- 关键数值均有来源，且单位没有混淆字符、token、字节与消息数。
- 主干机制、实验 feature flag、推测中的未来设计各自标明。
- 图表中的流程与正文一致，且不存在无来源的节点或数据。
- 每一个「因此」「所以」前面的证据，足以支持后面的推论。
- 已依据正文完成「理解检查」，能定位核心收获的支撑、跨节的实际关系及设计判断的适用条件，而非只检查导语承诺。
- 阅读顺序没有被误写为运行流程；贯穿性要求未被遗漏或硬塞成单一阶段，框架仍覆盖关键问题。
- 章节开头和机制切换处是否使用了明确实体名，而非需要回读才能确定对象的代词。
- 对每个影响系统边界的方案选择，是否说明了替代方案、取舍、适用场景，以及当前选择与本系统约束的关系。
- 读者能否只扫描标题、加粗、引用块、图表和代码块，就获取主要定义、关系与判断，并分辨事实依据、作者推断及关键边界，而不只是看到术语；正文是否仍提供必要解释。
- 若本文提供 AI 原创配图建议，是否按 [AI 原创配图建议](ai-illustration.md) 核验读者理解缺口、图片增量、prompt 的独立性及其不替代精确图表或源码证据的边界。
