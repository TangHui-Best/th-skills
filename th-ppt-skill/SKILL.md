# th-ppt-skill

按照“整体目标与主线 → 单页核心观点 → 图片呈现与迭代 → 可编辑 PPT → 逐页验收”的顺序工作。
用本技能确定内容、视觉和审视方法；制作文件时同时遵循当前环境的演示文稿技能与工具规范，生成图稿时遵循当前图像生成工具规范。

## 0. 素材分级与隐私边界

先区分任务材料：`公开`、`内部`、`受限`。客户名称、组织架构、路线图、系统拓扑、权限与日志覆盖范围、账号标识、真实数据、未发布产品信息及其截图，除非用户明确确认可公开，否则按`内部`或`受限`处理。

- `受限`材料不得上传、粘贴或作为参考图交给外部图像生成服务、在线设计工具或其他第三方服务。需要外部处理时，先取得用户对脱敏副本的明确授权；仅保留必要的视觉特征，不保留名称、数字、拓扑、日志或业务语境。
- `内部`材料默认只在当前受控工作区和最终获授权的交付物内使用。若要对外分享、发布或纳入通用技能包，先由用户确认分级和授权范围。
- 分类、客户事实、技术边界、建设状态、数据含义或可外发范围不明确且会影响内容或交付时，暂停并向用户询问；不得从上下文推断这些事实。仅可自行补全不改变事实的版式、留白等视觉细节。
- 交付前检查文字、图片、备注和文件元数据；移除令牌、账号、联系方式、内部路径、可识别业务标识及不必要的来源凭证。图中仍能推断出的架构信息也应按其分级处理，不能因没有明文凭据就视为公开。

## 1. 确定任务阶段

- 根据当前要求与已确认上下文判断任务：内容讨论、图片设计、按图制作、修改既有 PPT，或完成整套交付。
- 复用已确认内容、图片、风格和决策，以用户最新编辑的文字为基准。
- 用户只要求分析时先给分析；只要求画图时交付图稿；已确认图片并要求做 PPT 时直接制作，无需重新确认设计。
- 默认用先画图的方式探索新设计。整套新设计优先选择代表性页面建立版式，再扩展到同类页面。
- 用户要求“图满意后再做 PPT”时，先交付图稿，按反馈调整后进入文件制作。用户明确授权直接完成时，内部完成图稿与视觉检查后继续交付，不额外设置审批步骤。
- 缺少不影响事实的视觉信息时，可从材料与上下文推断；缺少会影响客户事实、技术机制、数据、权限边界或可外发范围的信息时，必须先澄清，同时继续独立可完成的工作。
- 用户的模板、品牌、页数、保留文字和指定版式优先于本技能默认建议。

## 2. 整体审视：主线、观点与用户收获

画图之前建立整体内容方案，明确以下信息。复杂任务使用 [内容方案模板](references/content-plan.md)，简单任务可在内部简要完成。

1. **目标用户**：受众的背景、关注点、已有认知与使用场景。
2. **表达目标**：整份 PPT 为什么需要存在，要回答哪些问题。
3. **内容范围**：哪些内容必须讲清，哪些延伸与目标无关。
4. **核心观点**：用一到两句话概括希望用户理解的主要判断。
5. **用户所得**：用户应获得什么信息、理解什么关系、作出什么判断或采取什么行动。不能只写“介绍产品”“展示能力”。
6. **叙事主线**：各部分如何支撑核心观点，是否自然递进，有没有重复、缺口与矛盾。

分别检查“作者想表达什么”和“用户实际获得什么”。内容完整和用户读懂是两个不同的检查项。
按受众选择深度：面向业务说明问题与影响，面向平台团队说明治理方案，面向开发者说明调用、机制与边界。不要把所有受众所需细节堆在同一页。

## 3. 单页审视：围绕核心观点组织表达

先为每页写一句：“这一页希望用户理解的核心观点是：……”。
用这句话指导标题、文案、案例和图示，再逐项检查：

| 检查项 | 要回答的问题 |
|---|---|
| 页面作用 | 用户为什么需要看这一页？它在整体主线中承担什么作用？ |
| 核心观点 | 希望用户理解的主要判断、关系或机制是什么？ |
| 支撑信息 | 哪些事实、步骤、案例或比较能支撑这个观点？ |
| 画面表达 | 用什么布局和视觉关系，使观点容易读出？ |
| 用户所得 | 用户实际能获取哪些信息？是否与表达目标一致？ |
| 判断价值 | 这些信息如何帮助用户理解问题或判断方案？ |

- 保持一页一个主要表达目标，允许多个支撑信息。不要为了“一句话”删除必要机制或证据。
- 保留用户认可的主题标题。标题可点明主题或表达观点，不强制改成口号或结论句。
- 用图示解释因果、流程、关系、边界或对比，不把大段文字仅换成装饰卡片。
- 让文案补充必要信息，减少重复表述、无关术语与过度口头铺垫。
- 只看页面，从用户视角用一句话复述观点，并指出能获得的具体信息。若只能复述“有很多功能”，继续修改。
- 演说词可以扩展解释，但关键结论、标签和限制仍需在页面中自洽。

## 4. 按页面职责选择表达方式

| 页面类型 | 重点呈现 |
|---|---|
| 业务挑战 | 用真实或明确标为示意的场景、问题、后果建立代入感，再归纳挑战 |
| 业界方案 | 讲清核心视角、典型问题、关键做法及启示，按需要深入机制 |
| 我们的方案 | 展示问题与设计选择的对应，以及各模块如何协同 |
| 关键能力 | 展示实现机制、使用变化、用户收益与职责边界 |
| 能力地图 | 用模块组织范围，区分父功能与子功能，标注经确认的建设状态 |
| 生命周期与流程 | 展示阶段、条件、责任方及事件顺序，不把相关事件误画成固定执行顺序 |

把故事用于帮助用户理解问题的页面，不要给每页重复套同一个业务故事，也不要把技术分析过度改写成泛化故事。

## 5. 呈现 AS IS / TO BE

- 在对比能解释方案或功能作用时加入 AS IS / TO BE。用户指定不需要对比或页面已清楚表达价值时，保留现有形式。
- **AS IS**：描述用户当前如何完成工作、困难在哪里，以及带来的成本或影响。
- **TO BE**：描述采用方案后，工作方式、判断依据或控制能力发生什么具体变化。
- **收益**：用一句话连接变化与用户所得，例如减少接入沟通成本、缩短故障排查时间、识别变更影响。
- 对齐同一维度比较，不能一边讲问题、另一边只罗列功能名。
- 不夸大现状，不宣称已有系统完全无法实现，不把设计目标写成已实现效果。
- 缺少客户现状依据时，将 AS IS 表达为典型问题或待验证假设，不伪装为已确认客户事实。

关键能力页可采用已验证的布局：左侧约 65%–70% 展示机制，右侧约 30%–35% 上下放 AS IS 和 TO BE，中间用向下箭头连接，底部放一句用户收益。
将其用于合适的同类页面，不强制整份 PPT 采用相同布局。

## 6. 先画图，再按确认图制作 PPT

1. 完成整体与单页内容方案，锁定必须保留的文字、事实与边界。
2. 选择代表性页面，生成完整幻灯片图稿。默认横版 16:9，用户参考或尺寸要求优先。
3. 在图稿要求中写清目标受众、核心观点、准确文案、布局、配色与禁止项。
4. 检查文字、信息层级、对象关系、箭头方向、视觉密度与留白，再按用户反馈迭代。
5. 对同类页面复用确认的视觉体系，保留不同页面的内容职责，不机械复制结构。
6. 图片确认后，重建原生 PPT 文字、面板和必要的可编辑图表、流程与连线。插图可以保留为图片素材。
7. 保持确认图的内容、观点、布局、配色和信息层级。为适应 PPT 字体调整换行或细微间距时，保留含义。

精确字段、复杂关系或数据不适合生成式图片时，用当前演示文稿工具绘制准确、可编辑的图稿并导出预览图，仍遵循先看图检查、再完成文件的顺序。
用户明确要求忠实保留原图或图片版 PPT 时按要求处理，不擅自重写文字或改变交付形式。

## 7. 简洁视觉规范

### 配色

- 默认白底，以黑色或深蓝正文、灰色辅助信息、蓝色强调为主。用户指定黑色时不要自行改成深蓝。
- 用绿色表达允许、成功或改善，红色表达拒绝、失败或风险；只在需要时使用，避免五种颜色平均铺满页面。
- 用浅灰呈现现状、浅蓝呈现改进或机制背景，保证背景与文字对比。
- 同类对象与状态使用一致颜色。建设进展先明确图例，再依据真实状态分配颜色；状态不明时标为待确认。
- 减少渐变、发光、纹理、复杂阴影和无关装饰；让插图与图标帮助识别对象、步骤或观点。

### 字体

使用一种包含所需字符的主要字体，通过字号、粗细和颜色建立层级。保留用户或模板规定的字体。
无指定模板时，以以下最终 PowerPoint 规格为默认起点，单位为 **pt（磅）**：

| 层级 | 建议字号 |
|---|---|
| 页面标题 | 32–36 pt，优先 32 pt |
| 模块标题 | 22–26 pt |
| 正文 | 18–22 pt |
| 辅助说明 | 14–16 pt，仅用于非核心信息 |

- 结合页尺寸、内容密度和投屏距离调整，不把字号范围当固定模板。
- 不把图片像素字号直接当 PowerPoint 的 pt，先确认渲染尺寸和单位再换算与检查。
- 内容放不下时优先精简、分组或调整布局，避免持续缩小字号。
- 验证字体文件完整可用，中文和特殊字符正常显示；检查实际导出页面，不仅检查源码中的字体设置。

### 对齐与留白

- 同类页面保持标题、分区、对比卡片、页码与收益条的位置和层级一致。
- 对齐卡片边缘、文字起点与同类图标，统一间距，采用稳定网格与边距。
- 将标签放在对应对象附近，让箭头避开文字，区分业务调用与治理关联等连接语义。
- 同类页面共用版式，不同类型页面按表达需要选择布局。

### 技术架构图的图标与表达

- 制作技术架构、系统集成、调用流程类页面时，读取 [技术架构图参考规范](references/technical-architecture.md)，查看其中的整页示例并按需选用独立图标。
- `assets/technical-architecture/reference-slide.png` 是通用技术架构视觉参考；仅复用其视觉搭配与关系表达，不将其中标签或拓扑自动当作新项目事实。若未来替换为客户、内部或受限材料，仍须先按本技能的素材分级与外部处理门禁执行。
- 将整页作为视觉搭配与关系表达示例，将独立图标作为可复用对象；按当前内容重新组织版式。
- 优先复用 `assets/technical-architecture/` 中的电脑、Agent、MCP工具和应用服务素材；保持等距视角、蓝青主色与少量黄色点缀。通过标签区分调用方Agent与业务Agent。
- 用具象图标表示参与方、工具与服务，用原生深蓝矩形表示网关，用浅蓝标签表示控制能力；让文字和连线保持可编辑。
- 按实际机制确定拓扑、协议、权限与观测边界。只连接已确认覆盖的组件，不能为追求对称补齐观测连线，也不能把参考图中的部署进展或数值作为新项目事实。
- 将这套视觉用于适合的技术页面；其他页面继续按内容选择表达方式，保留用户指定模板与品牌优先级。

## 8. 验收与交付

在当前演示文稿技能要求的结构校验之外，逐页渲染检查最终输出，使用 [验收清单](references/content-plan.md#验收清单)。

- 核对整体主线、核心观点、目标用户与用户收获。
- 核对每页观点、支撑信息与用户实际读出的信息是否一致。
- 核对页数、准确文字、必需标签、参考图内容及确认修改，避免图稿错字进入最终稿。
- 核对机制、因果、顺序、边界和职责，不虚构厂商能力、客户现状、数值或建设状态。需要当前事实时查证官方材料并按工具规则引用。
- 核对溢出、换行、遮挡、图标比例、配色与对齐。
- 核对原生内容可编辑；用户未要求图片版时，不把整页图片当可编辑页面交付。
- 核对素材分级、外部工具授权和输出文件元数据；不要在图稿、讲者备注、嵌入图片或导出文件中遗留受限材料。
- 对比确认图片与最终渲染，修复影响阅读和观点表达的差异，不仅凭导出成功判断完成。
- 按用户要求交付图稿或 PPT，遵循当前环境保存规范。简洁说明交付，不在幻灯片中写制作过程或验证日志。
